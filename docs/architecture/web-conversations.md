# Web conversations and outbound delivery

Portal messages use the authenticated actor's user, centre and subject. Requests contain only a client-generated message ID and text. The web repository upserts a conversation by centre, channel and portal user; it never accepts a conversation or subject ID from the browser. Parent and student identity is fixed once the conversation opens. Phone conversations continue through the original factory and address upsert.

The existing inbound store inserts with `ON CONFLICT DO NOTHING`. A duplicate is looked up only within the actor's conversation, so a client ID collision with another account cannot disclose its message ID. A new inbound row and its identifier-only outbox intent commit together; duplicate sends enqueue nothing. The provider uniqueness key includes the centre, allowing independent centres to use the same client ID.

The repository's Month 4 processing intent is named `InboundMessageReceived`; it does not yet have the `ProcessInboundMessageCommand` consumer assumed by the plan. Web ingestion reuses that existing intent. It is explicitly registered as deferred: the relay releases it for another check in five minutes without acknowledging or dead-lettering it, even after repeated intentional deferrals. Day 78 replaces this registration with its real consumer, and the pending rows resume automatically. Unknown message types still dead-letter immediately. Existing historical dead letters require an explicit recovery decision; this slice does not silently reprocess them or claim an agent response is produced.

Outbound messages follow queued → sent → delivered → read, with failed reachable only from queued or sent. Repeating the current state succeeds without changing stored identifiers, timestamps or failure details. Failed is terminal. A partial unique index makes one reply per inbound message structural. Composite foreign keys keep conversation and reply references within the same centre.

Only system actors hold the `conversations.ingest` capability used by send and delivery-status commands. Those commands have explicit outbox mappings containing IDs and status values, never text. The send handler locks the outbound row before invoking a registered channel adapter. Messages already sent or later, including failed messages, are not sent again. Retryable failures throw and roll back for the relay's backoff; permanent failures record a stable code. Web delivery succeeds immediately because polling reads the stored message. Unsupported channels have no fallback adapter.

The relay remains at least once. A future external adapter must use the outbound message ID for provider idempotency to cover a process crash after provider acceptance and before database commit. The row lock prevents concurrent sends and committed duplicates; it cannot create an atomic transaction with an external provider.

Messages are the conversation log and are intentionally excluded from the audit policy. Text is never included in outbox payloads or application logs. The outbound table has forced RLS and only SELECT, INSERT and UPDATE grants. The schema expansion preserves WhatsApp rows and replaces address non-nullability with a conditional address/portal-user constraint. Downgrade refuses while web-channel or outbound data exists, preserving that data rather than converting or deleting it.

Development seeding registers one `web:<centreSlug>` account per centre through the existing registration command. Web accounts have no display phone. Repeated registration returns the existing stable conflict code and does not duplicate accounts.
